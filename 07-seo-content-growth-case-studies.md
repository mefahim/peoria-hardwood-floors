# Phase 07 — SEO Content Growth & Case Studies

## 00. Purpose

Phase 07 expands the SEO system from governance into controlled content growth.

Primary goals:

1. Build a scalable content-growth framework.
2. Establish a safe case-study system.
3. Strengthen topical authority without creating thin or repetitive pages.
4. Improve internal linking between services, supporting content, and verified project evidence.
5. Preserve all Phase 02–06 SEO architecture and safeguards.
6. Ensure every published factual claim is traceable to verified business/project information.
7. Keep AI assistance strictly non-publishing unless a human-approved workflow already exists.

This phase must NOT become a mass content-generation exercise.

The objective is useful, evidence-based content that earns search visibility while remaining accurate, locally relevant, and maintainable.

---

# 01. Non-Negotiable Rules

The implementation agent MUST follow these rules:

- Do NOT invent projects, clients, locations, dates, prices, materials, measurements, outcomes, awards, certifications, reviews, ratings, memberships, guarantees, or business history.
- Do NOT create fictional case studies.
- Do NOT create location pages merely because a city exists in a service-area list.
- Do NOT create doorway pages.
- Do NOT create near-duplicate service/location articles.
- Do NOT create keyword-stuffed content.
- Do NOT publish AI-generated content automatically.
- Do NOT create pages solely to target individual keyword variations.
- Do NOT add fake testimonials or review markup.
- Do NOT add unsupported LocalBusiness data.
- Do NOT alter Phase 02 metadata authority.
- Do NOT replace the existing SEO resolver.
- Do NOT change canonical/robots/sitemap architecture except where explicitly approved by this phase.
- Do NOT add third-party SEO/content dependencies.
- Do NOT modify authentication, admin, API, database, payments, quota, or visualizer-generation systems.
- Do NOT change existing public URLs unless a redirect plan is explicitly approved.
- Do NOT create a CMS or database migration unless a later implementation stage explicitly authorizes it.

# 04. Content Growth Model

The content system should distinguish between:

1. Core service pages
2. Supporting educational content
3. Project/case-study content
4. Local content
5. Commercial/transactional support content
6. Utility pages

Each content item must have a clear purpose.

Every proposed content item must answer:

- What user problem does it solve?
- Which service/business capability does it support?
- What search intent does it address?
- What evidence supports the content?
- Which existing page should it strengthen?
- Which pages should link to it?
- Why does this deserve its own URL?

If these questions cannot be answered, the content should remain a planning item rather than become a published page.

# 05. Search Intent Taxonomy

Use these intent categories:

## Informational

The user wants to understand a problem, process, material, maintenance issue, comparison, or decision.

Examples of intent patterns:

- how does hardwood refinishing work
- how long does hardwood refinishing take
- hardwood floor maintenance
- sanding vs refinishing

Examples are intent patterns only. Do not automatically create pages for each phrase.

## Commercial Investigation

The user is evaluating options before contacting a provider.

Examples:

- hardwood refinishing options
- hardwood vs alternative flooring
- professional refinishing considerations
- what to ask a flooring contractor

## Transactional / Service

The user is seeking a service.

Existing service pages remain the primary target.

## Local / Service-Area

The user wants service availability in a verified location.

Only create location-specific pages when the location publication gate is satisfied.

## Project / Evidence

The user wants to understand what the business actually did on a real project.

Case studies belong here.

# 06. Topic Governance

Topics must be organized by:

- primary topic
- related topics
- search intent
- geographic relevance
- supporting service
- evidence status
- target page
- content status

Recommended lifecycle:

`IDEA → BRIEF → DRAFT → FACT_REVIEW → SEO_REVIEW → APPROVED → PUBLISHED → REVIEW`

No content may skip directly from IDEA to PUBLISHED.

AI-generated content must never bypass human fact review.

# 09. Content Quality Requirements

Every publishable content item should demonstrate:

### Relevance

Directly addresses a user need.

### Original usefulness

Adds practical information rather than repeating another page.

### Evidence

Business-specific claims must be supported by verified source material.

### Clarity

Content must be easy to scan and understand.

### Search intent alignment

The content must match why the user would search.

### Internal-link relationship

The page must have a meaningful relationship with existing content.

### Maintenance value

There must be a reason to keep the page current.

# 10. Case Study System

Case studies are a major Phase 07 feature.

However, case studies must be evidence-first.

A case study may only be published when sufficient verified project information exists.

Minimum recommended evidence:

- project identifier
- project type
- verified location, if publication is appropriate
- service performed
- verified project description
- available project images
- factual project details
- known constraints or goals, if documented
- documented work performed
- documented result/outcome, if available

Optional:

- materials
- finish
- approximate project scope
- timeline
- client-approved quote
- before/after imagery

Never infer missing information.

---

# 11. Case Study Content Structure

Recommended structure:

1. Project overview
2. Project context
3. Client/project goals — only if documented
4. Existing condition — only if documented
5. Work performed
6. Materials/finish — only if verified
7. Process
8. Visual evidence
9. Outcome — only if documented
10. Maintenance/next steps — only if relevant
11. Related service
12. Related educational content
13. Contact / estimate CTA

A case study should clearly distinguish:

- documented facts
- business-provided information
- client-provided statements
- editorial explanation

---

# 12. Case Study Schema

If case-study pages are eventually implemented, structured data must only describe information actually present on the page.

Do NOT misuse:

- Review
- AggregateRating
- Testimonial
- LocalBusiness
- Product
- Event

unless the relevant data is genuinely present and independently supported by the existing schema governance.

The case study itself should normally be represented as a WebPage/article-like content entity only if the existing architecture supports it.

Do not introduce a new schema architecture during Phase 07 without explicit approval.

---

# 13. Case Study URL Rules

Preferred pattern:

`/case-studies/[verified-project-slug]`

But:

- no route should be created until a real project exists
- slug must be stable
- slug must not expose sensitive client information
- location should only appear if appropriate and verified
- no fake case-study pages for SEO

If there are no verified projects, implement the framework only and publish zero case studies.

---

# 14. Local Content Safeguards

Local content must follow Phase 04.

A location may be published only when all required gates are satisfied.

Evidence may include:

- documented project
- verified service relationship
- unique useful content
- meaningful local context
- sufficient original value

A city name alone is insufficient.

A 75-mile service radius must never be converted automatically into dozens of city pages.

---

# 15. Cannibalization Controls

Before creating any content:

Check:

- same primary topic
- same search intent
- same geography
- same page purpose
- same service relationship

If an existing page already satisfies the intent, prefer:

- improving the existing page
- adding a section
- adding internal links
- improving supporting content

rather than creating another URL.

Lifecycle:

`FLAG → REVIEW → DECIDE`

No automatic consolidation or deletion.

---

# 16. Internal Linking

Internal links should be contextual and useful.

Recommended relationships:

Home
→ Services
→ Individual Service
→ Supporting Content
→ Case Study
→ Contact / Estimate

Supporting content should link back to the relevant service page.

Case studies should link to the relevant service.

Service pages may link to useful educational content and relevant verified case studies.

Avoid:

- footer link stuffing
- repetitive exact-match anchors
- irrelevant cross-links
- large blocks of automatically generated links

Anchor text should be natural and descriptive.

---

# 17. Content-to-Service Mapping

Every supporting content page must identify its primary service relationship.

Example:

```text
Topic: Hardwood Floor Refinishing Process
Intent: Informational
Primary Service: Hardwood Floor Refinishing
Primary URL: /services/hardwood-floor-refinishing-peoria-il
```

This allows content to strengthen the service architecture rather than compete with it.

STOP and report instead of implementing if:

- real project evidence is unavailable
- business facts conflict
- location evidence is insufficient

- dependency rollback
- URL migration
